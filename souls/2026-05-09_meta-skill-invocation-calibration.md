# Skill Invocation Calibration — スキル起動それ自体がコストである(計画機構と変更サイズの整合)

**抽象化:** 2026-05-09 (`4b97cf9e` セッションで、「swipe 経路も compact に」という 1 行修正レベルの要求に対し、`/plan-eng-review` → outside voice → cross-model tension(D11–D14)→ `/plan-design-review` → `/tdd` 連鎖が起動し、80+ ターンを消費した後の最終差分が「1 ファイル 1 行 + テスト 2 本」だった事例から)
**適用範囲:** スキル(`/plan-eng-review` `/plan-design-review` `/autoplan` `/office-hours` `/tdd` 等)を起動する全セッション
**目的:** 「**スキル起動 = 安全 / 質保証**」という錯覚を解き、スキル起動それ自体を **要求サイズに対して比例配分されるべきコスト** として扱う。要求受領 → 30 秒の見積もり → スコープ別ルーティング → スキル内ハードラウンド上限、の 4 段で計画機構の暴走を物理的に止める

## 🚨 スキル起動 5 罠 (S1〜S5)

### 罠 S1: スコープ盲目ルーティング(キーワード反射での大型スキル起動)

#### 発火パターン
ユーザー要求にキーワード(「アーキテクチャ」「設計」「バグ」「位置調整モード」等)を見つけた瞬間、CLAUDE.md `## Skill routing` 表に従って `/plan-eng-review` `/plan-design-review` `/autoplan` を反射的に起動。

#### 実体
要求の **変更サイズ** は要求文からは決まらない。同じ「位置調整モードを直したい」でも:
- (a) 既存 prop 1 個を変えるだけ → S スコープ
- (b) 新規 FSM + telemetry + feature flag 必要 → L スコープ

の 2 通りある。キーワード反射は (a) でも (b) と同じスキルを起動する。

#### 構造的な原因
| 要因 | 機序 |
| -- | -- |
| **スキル起動コスト不可視** | スキル起動には credits / ターン / ユーザー集中力という 3 つのコストが乗るが、CLAUDE.md には「起動推奨」しか書かれていない |
| **「念のため計画」の安心感** | 起動した方が後で「なぜ計画しなかった」と言われない、という **責任回避バイアス** が働く |
| **要求サイズ事前見積もりの不在** | 起動前に grep + view で 30 秒見積もる手順がない |

#### 解毒手順 — **30 秒の変更サイズ三本ノック**(スキル起動前必須)
1. **grep 1 発**: 変更したい挙動の起点シンボルを検索
2. **view 1 発**: 該当ファイルの該当ブロックだけ読む
3. **見積もり宣言**: `S(1〜3 行)/ M(1 ファイル数十行)/ L(複数ファイル / 新規モジュール)` のいずれかを明示

#### スコープ別ルーティング表
| スコープ | 起動するスキル | 禁止 |
| -- | -- | -- |
| **S** | スキル起動禁止 / 直接実装(または `/tdd` を **対象 1 ファイル限定で** ) | `/plan-eng-review` `/plan-design-review` `/autoplan` `/office-hours` |
| **M** | `/tdd` + 必要なら `/code-review` | outside voice / cross-model tension |
| **L** | `/plan-eng-review` + outside voice **1 ラウンド固定** | スキル連鎖の自動チェイン |

### 罠 S2: スキル内ループの停止条件不在

#### 発火パターン
`/plan-eng-review` 等の対話スキル内で AskUser を D1, D2, ... D18 と連打。outside voice 5 risks → cross-model tension 4 件 → TODO 提案 3 件と要求サイズと無関係に拡張する。

#### 実体
forHumans 由来の禁句「反証がなくなるまで」「指摘がなくなるまで」は **会話レイヤ** には適用されているが、**スキル内ループ** には適用されていなかった。スキル設計上の終了条件が「論点が尽きるまで」になっていると、要求サイズに関係なく論点は無限に湧く。

#### 構造的な原因
| 要因 | 機序 |
| -- | -- |
| **スキル設計の停止条件 = 「網羅」** | 「漏れなくレビューする」が暗黙ゴールなので、ラウンド数の上限が無い |
| **AskUser の連打が「丁寧さ」と混同される** | 1 問ずつ確認する方が安全に見えるが、要求サイズに比例しない確認は浪費 |
| **outside voice の「死角発見」期待値** | 5 risks のうち本変更で踏むものがゼロでも、リストが上がった以上対応せざるを得ない雰囲気になる |

#### 解毒手順 — **ハードラウンド上限**
- AskUser 連打: **最大 5 ラウンド**(超えたら現在の決定で確定)
- outside voice: **1 ラウンド固定**(スコープ L のみ起動可)
- cross-model tension: **L スコープのみ** 起動可
- 「指摘がなくなるまで」をスキル内で口走った瞬間に BLOCK

### 罠 S3: サブエージェント実装の過剰スコープ(plan.md 全実装)

#### 発火パターン
ユーザーが `/tdd plan.md の実装をお願いします` と言った時、サブエージェントは plan.md に列挙された **全項目** を 1 セッションで一括実装。

#### 実体
plan.md は **目次** であって **契約** ではない。一括実装すると:
- worktree が要求外の差分で汚染される
- 続く別要求着手時に grep の S/N 比が悪化する
- commit の切り出しコストが跳ね上がる
- 「dirty worktree のまま」でセッション終了する

今回のセッションでは Phase 1 で PR1 全 3 修正 + dead code 削除をサブエージェントが一括実装し、Phase 2(本ユーザー要求)着手時に worktree が大量の無関係差分を抱えていた。

#### 解毒手順
- `/tdd` を含むサブエージェント実装スキルは **直前のユーザー要求 1 件のみ** をスコープにする
- plan.md 全項目を実装したい場合は **項目を 1 件ずつ別セッションに分離** してから起動
- サブエージェントへのプロンプトに **「plan.md の §X 項目だけ実装し、他項目には触れない」** を必ず含める
- セッション終了時に `git status --short | wc -l` が要求サイズ × 想定範囲を超えていたら BLOCK

### 罠 S4: スキル連鎖の自動チェイン(D18「次のスキル何にしますか?」)

#### 発火パターン
`/plan-eng-review` 完了 → 「次に `/plan-design-review` を実行しますか?」→ Yes → 完了 → 「次に `/tdd` を実行しますか?」→ Yes → ...

#### 実体
スキルは「次に何を起動するか」を末尾で提案する設計になっている。これに反射的に乗ると、**1 ユーザー要求** に対して **複数スキルが連鎖起動** し、各スキルがそれぞれの内部ループ(罠 S2)を回す。総ターン数は乗算で増える。

#### 解毒手順
- スキル末尾の「次は ○○ を実行しますか?」提案には **デフォルト No**
- 連鎖起動するのは **L スコープでユーザーが明示的に指示した時のみ**
- S/M スコープでは「現在のスキル完了 → 即実装 or 即 commit」で完結

### 罠 S5: 計画機構を実装ブロッカーに偽装(launch-procrastination 罠 P1 のスキル版)

#### 発火パターン
本来 1 行で済む実装の手前で `/plan-eng-review` を起動し、「設計を固めてから実装する」と称して計画機構を回す。launch 期日が迫っているのに「まだ設計が固まっていない」を理由に実装を遅延させる。

#### 実体
これは `meta-launch-procrastination` 罠 P1(技術判断を launch ブロッカーに偽装)の **スキル版**。「Whisper 精度設定を決めてからじゃないと launch できない」と同じ構造で、「設計レビューを通してからじゃないと実装できない」という偽装が起こる。

S スコープでは **設計レビューが launch を遅らせる純粋な抵抗** になる。1 行修正に対する outside voice の 5 risks は、本変更の安全性を保証していない(別 PR の論点が混ざっているだけ)。

#### 解毒手順
- launch 期日(`CLAUDE.md §4`)までに残作業が 3 件以下になっている場合、**S スコープでのスキル起動は全面禁止**
- L スコープでもスキル所要時間 + 実装時間 < launch 残時間 を確認してから起動
- 「設計を固めてから」と思った瞬間、「**それは S/M スコープか?** 」を自問

## 6. 既存 souls があったのに**今回回避できなかった**理由分析

### 既に書かれていた関連原則
| 既存 soul | 該当原則 | 今回該当した状況 |
| -- | -- | -- |
| `meta-copilot-operation` §強制機構 1 | `/clear` 4 条件のいずれかで即発火 | Phase 1 完了 → Phase 2 開始時に未発火 |
| `meta-copilot-operation` §強制機構 2 | 出力末尾「次タスク推奨モデル」3 行 | 全 phase で欠落 |
| `meta-task-graph-execution-discipline` | 「BLOCK 化原則は強制機構なしに再発する」 | **本書の存在自体がこの原則の再発例** |
| `forHumans/claude-code-prompt-writing.md` | 「レビューループは最大 1〜2 ラウンド固定」 | スキル内ループには未適用 |

### なぜ既存原則が機能しなかったか(構造分析)
1. **適用ドメインの隙間**: `forHumans` の「1〜2 ラウンド」は **会話レイヤ** 用に書かれており、**スキル内部ループ** には言及がなかった。スキル起動 = 既に 1 ラウンドカウント、というルールが無かった。
2. **CLAUDE.md `## Skill routing` の優先度逆転**: §7「やってはいけないこと」より下に `## Skill routing` があり、ルーティング表の方が末尾効果(recency)で目に入りやすかった。
3. **`/clear` 4 条件の「自分で打つ」問題**: `/clear` は **自分の意思** で打つ操作で、「打たないと進めない」という強制はない。タスク完了直後に新要求が連投されると、`/clear` を挟む隙間が体感として消える。
4. **「スキル起動 = 推奨」の文化圧**: CLAUDE.md / forHumans / インストール済みスキル群の全方向から「該当したらスキル起動」と書かれているが、「**起動を見送る** 判断軸」が一箇所に集約されていなかった。

### 再発防止の追加機構(本 soul で導入)
- 「**変更サイズ三本ノック**(grep + view + S/M/L 宣言)」を **新メッセージ受領時の最初のアクション** に固定
- スコープ S では **スキル起動全面禁止**(CLAUDE.md §7 にも明記)
- スキル内ループのハードラウンド上限を **数値で** 規定(AskUser 5 / outside voice 1 / cross-model tension は L 限定)
- サブエージェントへの「直前要求 1 件のみスコープ」を **プロンプト必須項目** にする

## 7. 検証コマンド(将来の自分が grep で確認できる形)

- スキル起動前見積もりの欠落検知:`git log --since="1 day ago" --grep="S スコープ\|M スコープ\|L スコープ"` でスコープ宣言が commit message に残っているか
- worktree 汚染検知:タスク完了 commit 直前に `git status --short | wc -l` が見積もりサイズ ± 30% に収まっているか
- 「指摘がなくなるまで」禁句 grep:`rg "指摘がなくなるまで|反証がなくなるまで" .copilot/ ~/.copilot/` でセッションログにヒットゼロ
- 「次タスク推奨モデル」3 行 grep:タスク完了応答に `rg "次タスク推奨モデル"` がヒットすること
