# タスクグラフ実行規律 — 依存・削除順序・PARTIAL 証跡の運用ゲート

**抽象化:** 2026-04-26 (`task_64〜71c 振り返り` で見えた 5 教訓のうち、既存 souls で扱っていない「タスク間の運用層」の問題を統合)
**適用範囲:** 複数タスクが波 (Wave) として直列・並列に走るプロジェクト全般 (UI 機能追加 / 大規模リファクタ / state 拡張を含む変更)
**目的:** 個々のタスク内の実装ゲート (テスト緑 / build 緑 / 5 軸セルフチェック) を全て通しても、**タスク間の依存関係・順序・証跡** が崩れていれば成果物は壊れる。タスクグラフ層に独立したゲートを敷く

---

## 🧬 前提 — 「タスク内品質」と「タスク間品質」は別物

既存 souls は **タスク 1 本の中** で起きる事故を扱ってきた:

| 既存 soul | 守備範囲 |
| -- | -- |
| `meta-browser-runtime-asymmetry` | 1 タスク内の実装が実機で壊れる 5 軸 |
| `meta-requirement-translation-traps` | 1 タスクの設計が要求を裏切る 5 罠 |
| `meta-spec-phase-hallucination` | 1 spec / task ファイルに混入する架空型・API |
| `meta-debugging-when-stuck` | 1 タスクの実装が詰まった時の突破 |

しかし `task_64〜71c` (12 タスク 3 日) の振り返りで判明したのは、**全タスクがそれぞれ単体では緑** にも関わらず以下が起きていたこと:

| 事故 | 該当タスク | 単体テスト | 実機 | 全体システム |
| -- | -- | -- | -- | -- |
| 依存逆転 (波形が global seekbar に乗らず分割モード専用化) | task_68 | ✅ | ✅ | ❌ (要件未充足) |
| 削除先行による機能消失 (時間調整 UI が一時的に存在しない) | task_69a | ✅ | ✅ | ❌ (代替が無い) |
| PARTIAL のまま完了扱い (実機証跡が残らない) | task_66, task_71c | ✅ | ? | ❌ (再現不能) |
| 初回実装で cleanup 忘れ → 別 commit で個別修正 | task_71c → 96a543b | ✅ | ✅ | ⚠️ (履歴汚染) |

**根本構造:** タスク内の品質ゲート (テスト・build・実機セルフチェック) は **「そのタスクが正しく動くか」** しか保証しない。**「そのタスクが正しい順序で / 正しい依存先と / 正しい証跡付きで完了したか」** は別の層で保証する必要がある。

## 🚨 タスクグラフ層の 5 ゲート

### ゲート 1: Wave 依存元の完遂確認 (Dependency Gate)

#### 発火パターン

「Wave2 の task_65 (グローバルシークバー) が未着手なのに、それに乗ることを前提にしていた task_68 (波形) と task_69a (TIME_ADJUST 削除) が先行実装された」

#### 観測可能な事実

- spec 段階で「依存タスク: task_65」と書いていても、**着手判定の自動ガード** は無い
- 1 セッション 1 タスクの規律 (`forHumans/claude-code-prompt-writing.md` 原則 1) は **タスク間の前後関係** を会話で繋がない以上、各セッションは「自分の親タスクが終わっているか」を **明示的に確認しない限り知らない**
- 結果、依存ツリー上の親が空のまま子だけが完了し、システムは「子は動くが親が居ない」状態に陥る

#### テスト / レビューで捕まらない理由

- 単体テスト・E2E は該当タスクの範囲だけを検証する。**親タスクの存在** はテスト対象外
- code review も diff の妥当性しか見ない (依存元タスクのソースを開かない)
- 「依存タスクは別 PR でカバー」という発言が **アリバイ化** して放置される

#### 解毒手順

1. Wave 開始セッション冒頭で **依存元タスク完遂確認** を強制する手順:
   ```bash
   # 着手予定タスクの依存タスクが commit / 実装ファイルとして実在するか
   rg -n "依存タスク[:：]" tasks/task_<新規>_*.md
   # 列挙された各タスクについて:
   git log --oneline --all -- "tasks/task_<依存>_*.md" | head -5
   ls -la <依存タスクが生成すべき実装ファイル>
   ```
2. 依存元の **commit が実在し、かつ実装ファイルが grep で 1 件以上ヒット** することを確認してから着手
3. 依存元が空なら:
   - (a) 依存元タスクを先にこのセッションで完遂する、または
   - (b) 「依存元なしでも成立する最小スコープ」に当該タスクを再分割する (依存解除)
4. spec の「依存タスク」欄が **空** または **`なし`** と書かれているタスクのみ、依存確認をスキップ可

#### シグナル

- spec の「依存タスク」欄に書かれたタスク ID を **commit log で grep していない**
- 「task_X は別 PR で対応予定」という発言が spec / 会話に出る
- 依存元タスクの実装ファイル (`<feature>.tsx`) を `find` / `rg` で確認していない

### ゲート 2: 削除タスクは「代替の完了」が前提 (Deletion-Replacement Gate)

#### 発火パターン

「グローバルシークバーが入る前提で `TIME_ADJUST` state を先に削除した結果、グローバルシークバーが未着手のため時間調整 UI が一時的に消失した」(task_69a)

#### 観測可能な事実

- 削除タスクは「コード行数を減らす」というポジティブな成果として承認されやすい
- しかし削除した機能の **代替提供元** が未完成だと、**代替が来るまでの期間** はシステムが機能不在になる
- 単体テストは「削除した state が無いこと」を assert するため緑になる。**代替が存在することを assert するテスト** は通常書かれない

#### テスト / レビューで捕まらない理由

- 削除タスクのテストは「削除されたコードが呼ばれない」を検証するもの。代替の存在は範囲外
- レビュアーは diff の minimal さを評価し、「代替先の存在確認」を盲点化しがち
- 「代替は task_X で来る」というコメントは spec/PR description に書いても **実装着手の物理ガード** にはならない

#### 解毒手順

1. 削除タスク (`tasks/task_*` で `削除` / `撤去` / `removeFoo` などを含む) の spec に **完了条件の追加項目** として:
   ```
   - [ ] 代替機能 (task_<代替>) が **commit 済み** かつ **動作確認済み** であること
   ```
   を必須化
2. 代替が未完なら削除タスクを **着手しない** (spec 完成度に関わらず)
3. やむを得ず先行削除する場合、`feat:` ではなく `wip:` プレフィックス commit にして「代替合流まで未完」を明示
4. 削除タスクのテストは、代替機能の存在を **smoke check** で assert する 1 件を必ず含める (例: 「時間調整可能な UI 要素が DOM に存在する」)

#### シグナル

- 削除タスクの spec に「代替: task_X」と書いてあるが、task_X の実装ファイルが grep で空
- commit log で「削除」commit が代替実装 commit より先に並んでいる
- ユーザーの動作確認で「あれ、X 機能どこ行った?」と聞かれる
- 削除タスクのテストが「無いこと」しか検証していない

### ゲート 3: PARTIAL は「実機証跡」を残すまで完了扱いしない (Evidence Gate)

#### 発火パターン

「タスク完了報告に `PARTIAL=Yes` と書いたが、実機確認結果 (端末 / 日付 / 観察) が knowledges/ に残らなかった結果、後セッションで『これ実機で動いてたっけ?』が再現不能になる」(task_66 スワイプ, task_71c 長押し D&D)

#### 既存 soul との関係

`meta-browser-runtime-asymmetry §ゲート A` は **「PARTIAL タスクは実機テスト対象外 (実機に出さない)」** を規定する。本ゲートはその **裏側**: **「PARTIAL を完了扱いに昇格させるには実機証跡を残せ」**。両者はペア:

| ゲート | タイミング | 役割 |
| -- | -- | -- |
| 既存 ゲート A | 実機テスト **前** | PARTIAL を実機に持ち込むのを禁止 |
| 本 ゲート 3 | 実機テスト **後** | 実機で確認したことを証跡として固定化 |

#### 観測可能な事実

- PARTIAL タグは「実装は緑、実機確認はこれから」のメタフラグ
- 実機確認は **数分の操作** で済むが、結果を記録する習慣がないと「やったかやってないか」が誰にも分からない
- 後セッションは git log と knowledges/ を頼りに状態を再構築する。**証跡が無い PARTIAL は「未確認かもしれない」状態として永久に残る**
- 「実機で動いた、覚えてる」という人間の記憶は 1 週間で蒸発する

#### 解毒手順

1. PARTIAL タスクは knowledges/ に **実機確認セクション** を必ず残す:
   ```markdown
   ## 実機確認
   - 日付: 2026-04-26 14:30
   - 端末: iPhone 14 (iOS 17.4) / Safari
   - 確認内容:
     - [x] 長押し 500ms で position drag 起動
     - [x] 10px 移動でキャンセル動作
     - [x] BottomSheet オープン中の back gesture 挙動
   - 観察された差分: <あれば記載 / 無ければ「想定通り」>
   ```
2. このセクションが knowledges/ に commit されるまで、PARTIAL タスクの完了報告は **禁止**
3. CLAUDE.md §6 (やってはいけないこと) に「実機確認なしで完了報告」を BLOCK 化済み — これに **「証跡なしで完了報告」も同等扱い** を追記
4. PARTIAL タスクの spec 完了条件チェックリストに「knowledges/ に実機確認セクションを追加」を 1 行入れる

#### シグナル

- 完了報告コミットメッセージに「実機確認した」とあるが knowledges/ に該当ファイルが無い
- 後セッションで「task_X って実機で動いてた?」と聞かれて答えられない
- PARTIAL タスクが連続で並んでいるが knowledges/done/ の追加ファイルがゼロ

### ゲート 4: state 拡張 UI は a/b/c で物理的に順序強制 (Decomposition Gate)

#### 発火パターン

「state 拡張 + モーダル + ジェスチャを 1 タスクで束ねると、テスト・実装・実機確認のいずれかで詰まったときに **どの層が原因か切り分け不能** になる」

逆に成功例 (task_71a → 71b → 71c) では:
- 71a: FSM に `POSITION_DRAG` / `POSITION_ACTION` state 追加 (ロジック層単独)
- 71b: `PositionActionModal` 単体実装 (UI 単独)
- 71c: `useLongPress` でジェスチャ統合 (ジェスチャ層)

各段が **独立にテスト緑** で次段着手可能。

#### 観測可能な事実

- 「state 拡張 + UI + ジェスチャ」を 1 タスクに束ねると、テストファイルが 3 つの責務 (FSM / レンダリング / 入力) を同時に検証することになり、失敗時の切り分けが困難
- 1 commit に 3 層分の変更が混ざり、後から `git revert` / `git bisect` で部分ロールバックが効かない
- AI 実装は 1 タスク内のスコープが広いと、3 層のうち最弱の層 (たいていジェスチャ) を後回しにして「動いた」と報告しがち

#### 解毒手順

1. **state 拡張を伴う UI 機能** は spec 段階で a/b/c 命名で 3 タスクに分割する規則:
   - `task_NNa`: state / FSM 拡張 (ロジック単独、UI 変更なし)
   - `task_NNb`: 新規モーダル / パネル / コンポーネント単体 (UI のみ、入力はキーボード操作のみ)
   - `task_NNc`: ジェスチャ / 長押し / D&D 統合 (入力層、a と b の合流)
2. 各段の完了条件:
   - a: 単体テスト緑 + FSM 状態遷移図が更新されている
   - b: コンポーネント単体テスト緑 + Storybook なり単独画面で目視確認
   - c: 結合テスト緑 + 実機確認証跡 (ゲート 3 適用)
3. a/b/c のうち先行段が未完なら次段着手禁止 (ゲート 1 と同じ依存原則)
4. state 拡張を伴わない (UI のみ / ロジックのみ) タスクは分割不要

#### シグナル

- 1 タスクの完了条件に「FSM 拡張」「新規コンポーネント」「ジェスチャ統合」が **全て** 並んでいる
- テストファイルが 3 つの責務を同時に検証している (FSM / Render / Touch event)
- 1 commit の diff が 5 ファイル以上で、責務がバラバラ

### ゲート 5: custom hook の cleanup を初回実装でテンプレ化 (Cleanup Template Gate)

#### 発火パターン

「`useLongPress` 初回実装で `setTimeout` のクリーンアップが抜けており、アンマウント後にタイマーが発火する不具合が follow-up commit (96a543b) で個別修正が必要だった」

#### 観測可能な事実

- React の custom hook で `setTimeout` / `setInterval` / `addEventListener` / `requestAnimationFrame` を持つときの cleanup 忘れは 1 タスク内の実装ミス **だが** 同一プロジェクトで複数の hook を作る過程で **同じ忘却が反復する**
- 単体テストではアンマウント後の挙動を検証しないことが多く、テスト緑のまま流れる
- 既存 soul `meta-browser-runtime-asymmetry §軸 1 (event loop 順序)` と §軸 3 (passive listener) の親戚だが、それらは「実装するときにやるべき」を扱う。本ゲートは「**custom hook を新規作成するときのテンプレ**」として運用層に降ろす

#### 解毒手順

1. 新規 custom hook を作るときのテンプレート (snippet 化推奨):
   ```typescript
   export function useFoo(...) {
     // 1. 副作用が握るリソースをローカルに宣言
     const timeoutRef = useRef<number | null>(null)
     const listenerRef = useRef<((e: Event) => void) | null>(null)

     useEffect(() => {
       // 2. setup

       // 3. cleanup を **必ず** 書く (空でも書く習慣)
       return () => {
         if (timeoutRef.current !== null) {
           clearTimeout(timeoutRef.current)
           timeoutRef.current = null
         }
         if (listenerRef.current) {
           target.removeEventListener('xxx', listenerRef.current)
           listenerRef.current = null
         }
       }
     }, [...])
   }
   ```
2. spec のセルフチェックに 1 行追加:
   - [ ] custom hook で `setTimeout` / `addEventListener` / `requestAnimationFrame` を握る場合、`useEffect` の return で cleanup を書いた
3. 既存 hook の grep 棚卸し (BLOCK 化と同時に legacy cleanup タスクをペアで立てる、`meta-browser-runtime-asymmetry §共通根本原因` の運用):
   ```bash
   rg -nU "setTimeout|setInterval|addEventListener|requestAnimationFrame" hooks/ lib/ components/ | \
     rg -v "return \(\) =>" -C 3
   ```
4. ESLint rule (`react-hooks/exhaustive-deps` + custom rule) で機械検出を検討

#### シグナル

- 新規 hook の `useEffect` に return が無い
- 同一 hook を別 commit で「cleanup 追加」修正している (本事例 96a543b)
- アンマウント時の挙動を検証する単体テストが無い

## 🛡️ 着手前チェックリスト (Wave / セッション開始時に全件回す)

### A. 依存ゲート

- [ ] このタスクの spec の「依存タスク」欄を読んだ
- [ ] 各依存タスクの commit が実在することを `git log` で確認した
- [ ] 各依存タスクが生成すべき実装ファイルが `rg` / `find` で 1 件以上ヒットした
- [ ] 依存元が未完なら、依存解除 (再分割) または依存元先行のいずれかを選んだ

### B. 削除ゲート

- [ ] このタスクが「削除」「撤去」を含むなら、代替機能タスクの完了を確認した
- [ ] 代替が未完なら本タスクを着手しない (もしくは `wip:` プレフィックスで commit する覚悟)
- [ ] 削除後のテストに「代替の存在 smoke check」を 1 件含めた

### C. 分割ゲート

- [ ] このタスクが state 拡張 + UI + ジェスチャ を含むなら、a/b/c に分割されているか
- [ ] 各段が独立したテスト緑で完了する設計か
- [ ] 先行段が未完のまま次段に進んでいないか

### D. cleanup ゲート

- [ ] 新規 custom hook で `setTimeout` / listener / rAF を握る予定なら、`useEffect` cleanup テンプレを最初から組み込んだ
- [ ] 既存 hook を編集する場合、cleanup の有無を `rg` で確認した

### E. 証跡ゲート (PARTIAL の場合)

- [ ] 完了時に `knowledges/` に実機確認セクション (日付・端末・観察) を残す予定がある
- [ ] 完了報告 commit より前に実機確認 commit を入れる順序を計画している

## 🔍 既存 souls との関係 — なぜ既存原則で防げなかったか

### 重複 1: `meta-browser-runtime-asymmetry §ゲート A` (PARTIAL を実機に出さない)

- **既存原則:** PARTIAL タスクは実機テスト対象外
- **本書ゲート 3 との違い:** 既存は「実機に出すな」、本書は「実機で確認したら証跡を残せ」
- **なぜ既存だけでは防げなかったか:** 既存原則は「実機に出さない」までしかカバーしない。実機で確認した **後** の証跡管理が運用の盲点だった。本書ゲート 3 を **既存 ゲート A の対** として追記することで両端を閉じる

### 重複 2: `meta-browser-runtime-asymmetry §共通根本原因` (原則追加と legacy cleanup はペア)

- **既存原則:** 原則を追加したら既存コードの legacy cleanup タスクを必ずペアで立てる
- **本書ゲート 5 との関係:** ゲート 5 は custom hook の cleanup テンプレを **初回実装段階** で組み込む規律。既存原則は **legacy 棚卸しタスクの運用** を扱う
- **なぜ既存だけでは防げなかったか:** 既存原則は「原則追加時」のフックしかなく、新規 hook 実装時のテンプレ強制ガードが無かった。本書ゲート 5 で初回実装側を補う

### 重複 3: `meta-requirement-translation-traps §γ` (grep で既存 API 列挙)

- **既存原則:** CRUD 動作を書く前に grep で既存 specific API を列挙
- **本書ゲート 1 との違い:** 既存は **API レベル** の grep、本書は **タスクレベル** の依存確認 (commit log + 実装ファイル grep)
- **なぜ既存だけでは防げなかったか:** API 地図化は「同一タスク内」の話で、タスク間の依存ツリーは別の grep 対象。両者は orthogonal なのでペアで運用する

### 重複 4: `forHumans/claude-code-prompt-writing.md 原則 1` (1 タスク = 1 セッション)

- **既存原則:** 1 タスクごとに commit してセッション閉じる
- **本書ゲート 1 との関係:** 1 セッション 1 タスクは「タスク間を会話で繋がない」規律。本書ゲート 1 はその副作用 (依存元の状態を会話で確認できない) を **セッション冒頭の grep ガード** で補う
- **なぜ既存だけでは防げなかったか:** 既存原則は session 設計の話で、依存ツリーの **着手判定** までは要求していない。本書ゲート 1 で「新セッション開始 → 依存元 grep → 着手判定」の物理ガードを追加する
