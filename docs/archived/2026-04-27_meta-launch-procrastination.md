# Launch 先送りと「もう一機能だけ」の罠 — 完璧主義を期日で殺す

**抽象化:** 2026-04-27 (`/office-hours` セッションでの「Whisper 精度を tiny→base に上げるべきか」「速度 vs 精度どちらをデフォルトにすべきか」議論が、本質的には **launch 行動の先送り** だったと判明)
**適用範囲:** プロダクト / 新機能 / 個人プロジェクトの **「未だ 1 人もユーザーに触ってもらっていない」状態** からの脱出フェーズ全般
**目的:** 技術的判断に偽装された launch 先送りを早期検知し、**期日コミットメント** で完璧主義を物理的に殺す
**関連:** `knowledges/done/2026-04-27_office-hours_launch-strategy.md` (本書の発火元 / 期限コミット 2026-05-03)
**改訂:** v1.1 (2026-05-08) — `2026-05-04_b2b-pivot-ux-bugs-strategy-retrospective.md` 統合。3 点追加: (a) **罠 P6「ペイン不在を打席数不足に誤帰因する」** を新設 — B2B コールドメール 6 社送信→返信ゼロを「6 社では足りない (罠 P3)」と再解釈しかけたが、根本原因は **ペイン validation 3 問が事前に立てられていなかった** こと。罠 P3 (打席数で需要不在を結論するな) は false negative on demand を防ぐが、**「pain validation 不在を打席数で説明する」逆罠** を防げなかった。(b) **罠 P3 解毒手順に追記**: 打席数を追加投入する **前に** 「ペイン validation 3 問」(払っているか / 困っていると自発的に言うか / 放置コストが数値化できるか) を再確認する。3 つ全て YES でないなら追加打席ではなく **顧客プロファイル変更** に投資する。(c) チェックリストに **F セクション「Pain validation」** を追加。**メタ教訓: 罠 P3 は「打席不足で需要不在を結論する」を防ぐが、その逆「需要不在を打席不足で説明する」も同じくらい毒。打席数に手を伸ばす前に Pain validation 3 問を必ず通す。**

---

## 🧬 前提 — 「技術的に決まらない」と「launch を始めない」は別の話

ビルダーは **技術判断** と **launch 行動** を脳内で同じトレイに積みがちである。しかし両者は次元が異なる:

| 軸 | 技術判断 | launch 行動 |
| -- | -- | -- |
| 解決手段 | 比較・実験・ベンチマーク | 送信ボタンを押す |
| 完了条件 | データに基づく結論 | ユーザーが触る |
| 先送り時の自己説明 | 「最適解が定まらない」 | (技術判断にすり替えられる) |
| 真のリスク | 局所最適化に時間を使い過ぎる | **永遠に launch しない** |

技術判断を「launch ブロッカー」と誤分類する瞬間に、**launch は無期限延期** される。本書はその誤分類を 5 つの罠として捕獲する。

---

## 🚨 Launch 先送り 5 罠

### 罠 P1: 技術設定の最適化を「launch 前提条件」に偽装する

#### 発火パターン

「Whisper の精度を tiny にすべきか base にすべきか決まらないので launch できない」

#### 実体

精度設定は **ユーザー反応データが取れる前は理論的にしか決められない**。実ユーザーが「速度優先」を求めるか「精度優先」を求めるかは、**5〜10 人にコールドメールを送って反応を見る以外に取得手段がない**。つまり:

- 精度を決めるためには launch が必要
- launch を止めて精度を決めようとしても、**情報源が無いので決まらない**
- 結果、launch しないループに永久に閉じ込められる

#### 構造的な原因

| 要因 | 機序 |
| -- | -- |
| **builder の「正解先決」癖** | デフォルト値を最適化してから出すのが「品質ある仕事」だと内面化している |
| **データなき最適化の幻想** | 仮説と実データの区別が曖昧で、仮説を「もう少し練れば確定する」と思い込む |
| **launch リスクの過大評価** | 「精度が低くて使われなかったら」を恐れるが、**そもそも触られなければ精度の優劣すら検証されない** |

#### 解毒手順

1. 技術判断のブロッカーが浮上した瞬間、**「これは launch 後に決められる判断か?」** を 1 行書いて自問
2. launch 後に決められる判断ならば、現状のデフォルトのまま **launch 行動を先に進める**
3. デモや初回印象だけ品質を上げる必要がある場合は、**デフォルトは触らずに手動処理した結果を添付** する (本事例: アプリ内デフォルト=tiny / コールドメール添付=base 手動処理)
4. 「決められない」を `tasks/` の課題ではなく `knowledges/open-questions.md` に降格 (launch ブロッカーから外す)

#### シグナル

- 技術設定の比較表を作っているが、決定基準が「ユーザーがどう感じるか」 → ユーザーがいない
- 「もう少しデータがあれば決まる」 → そのデータの取得経路が launch しかない
- spec / tasks に「<設定> を最適化してから launch」と書かれている

### 罠 P2: 「もう一機能だけ」の入口検知

#### 発火パターン

「改行機能を入れてから launch したい」「誌字検出があった方が感動が大きい」「見栄え編集 UI をもう少し綺麗に」

#### 実体

「もう一機能だけ」は **常に複数形** で発生する。1 つ追加すると次の 1 つが見えてしまうため、追加リストは**自己生成**する。各機能はそれぞれ単独で見ると合理的に見える (改行は確かに便利、誌字検出は確かに価値ある) が、**全体としては期日を破壊する**。

| 提案の典型 | 表面の合理性 | 真の効果 |
| -- | -- | -- |
| 「改行機能」 | テロップ視認性向上 | +工数 N 日 → 期日破壊 |
| 「誌字検出」 | ユーザー価値向上 | +工数 M 日 + 設計再考 → 期日破壊 |
| 「もう少し綺麗な UI」 | 第一印象向上 | +工数 ∞ → 永久 launch しない |

#### 構造的な原因

- **タスト由来の良心**: builder にはプロダクトに対する taste があり、「これは出せる品質ではない」と自然に感じる
- **未触体験の理想化**: ユーザーが触る前は理想像しか無いので、その理想に近づけ続けたい
- **失敗の予測恐怖**: 「機能不足で否定されたら」を恐れるが、**機能過剰で出さないことの否定 (= 永久に検証されない)** はもっと致命的
- **「感動を与えたい」**: ✨ で言語化できる感性は資産だが、**「使うタイミング」の判断が誤る**と毒に変わる

#### 解毒手順

1. 「もう一機能だけ」を考えた瞬間、その機能を **`anti-goals.md` に書く** (「絶対にやらない」リスト)
2. MVP の定義を **「感動機能完備」ではなく「信頼破壊バグなし」** に固定
   - 信頼破壊バグ = 「ユーザーが二度と触らなくなる」レベルのバグ (preview/export 不一致 / 操作不能化 等)
   - その他の機能不足は「次の機能追加で改善」で構わない
3. 期限まで残りの作業を **3 つだけ書く** (4 つ目は無条件に切る):
   - 本事例: P0 バグ #1 修正 / P0 バグ #3 修正 / コールドメール送信
   - これ以外は launch 後に
4. `taste` は 5/3 (期日) 後に **2 周目** で使う。`taste` の使用タイミングをずらすだけで完璧主義の毒は抜ける

#### シグナル

- 残作業リストが期限直前で増えている (減らない)
- 「これも入れたら…」「あと一つだけ…」を口に出している
- 機能追加の根拠が「自分が触って嬉しい」 (= ユーザー証拠でない)
- 「感動を与えたい」が launch 期日と競合している

### 罠 P3: 打席数が 1 で需要不在を結論する

#### 発火パターン

「3 件 DM を送ったが返信が無いので、需要が無さそう」「Yahoo 知恵袋に投稿したが反応ゼロなので、ターゲットが間違っているのかも」

#### 実体

打席 1〜3 件は **統計的に意味のあるシグナルにならない**。コールドメール / DM の返信率は良くて 5〜10%。3 件で 0 返信は「需要なし」ではなく「サンプル不足」。**5〜10 件を同時送信して初めて、返信率 0/5 は「文面 / ターゲット見直し」のシグナルになる**。

| 打席数 | 返信 0 の意味 |
| -- | -- |
| 1 件 | ノイズ (何も言えない) |
| 3 件 | ノイズ (何も言えない) |
| 5〜10 件 | 文面・ターゲット見直しのシグナル |
| 20+ 件 | 需要不在の有意な可能性 |

#### 構造的な原因

- **「行動した」感の早期消費**: 1 件送って待つと、行動した気持ちで安心して次が動かない
- **拒絶への耐性不足**: 5 件送って 5 件無視されるほうが 1 件無視されるより心理的負担が線形に増えない (むしろ慣れる)
- **間隔を空ける錯覚**: 「順次送って反応を見ながら」が一見賢いが、各送信は独立事象で **同時送信のほうが情報量が多い**

#### 解毒手順

1. 初回 launch の打席数は **5〜10 件を最低ライン** とする (1 件は launch ではなく試射)
2. 同時送信のために **送り先 5〜10 社を spreadsheet 化** してから送信開始 (バッチ準備)
3. 返信率の判定は **全件送信完了 + 1 週間待機後** に行う (途中経過で結論しない)
4. 0 返信 → 文面 / ターゲット見直し (need search) / 1 件以上返信 → 次フェーズ (デモ → 継続使用 → 課金)
5. **(v1.1 追加 / 罠 P6 連携) 打席数を追加投入する前に「ペイン validation 3 問」を必ず再確認**: (1) 払っているか / (2) 「困っている」と自発的に言うか / (3) 放置コストが数値化できるか。3 つ全て YES でないなら **追加打席ではなく顧客プロファイル変更** に投資する (打席数を増やしても無意味)

#### シグナル

- 「1 件送ってみて様子を見る」と言っている
- 送信先リストが 1〜3 件
- 返信ゼロを「需要なし」の証拠として扱おうとしている
- 「もう少し DM 送ったら反応あるかも」 ← 5〜10 件まとめて送る発想が無い

### 罠 P4: 期日を「目標」にして「コミット」にしない

#### 発火パターン

「来月くらいまでに launch できたらいいな」「準備が整ったら launch」

#### 実体

「目標日」と「コミット日」は **物理的に別の概念**:

| 種類 | 期日 | 期日後の挙動 |
| -- | -- | -- |
| 目標 | 「できれば」「だいたい」「来月」 | 過ぎても何も起きない (静かに延期) |
| コミット | 絶対日付 (2026-05-03 (日) 23:59) | 過ぎたら **失敗** として記録される |

「目標」しか持たない builder は、無限に期日を後ろにずらせる。コミットは過ぎた瞬間に **「失敗」というラベルが立つ** ため、それを避けるための行動圧力が生まれる。

#### 構造的な原因

- **柔軟性志向**: 「状況に応じて調整」が builder の合理的習慣だが、launch では **柔軟性 = 永久延期** に化ける
- **失敗ラベル恐怖**: コミットを切ると失敗が記録される。だから切らない
- **進捗錯覚**: 進捗があれば「進んでる」気持ちで、期日が漠然とでも問題視されない

#### 解毒手順

1. 期日は **絶対日付 (年月日 + 曜日 + 時刻)** で書く: `2026-05-03 (日) 23:59`
2. その日付を **カレンダーアプリにブロックとして入れる** (mental note ではない)
3. 期日条件は **複数の検証可能な完了項目** に分解:
   - 「launch する」ではなく
   - 「P0 バグ #1 修正済み」「P0 バグ #3 修正済み」「公開 URL 確保」「5〜10 社送信完了」「結果を knowledges/ に記録」
4. 期日後の **失敗時の挙動** を事前に書く: 「5/3 までに送信完了しなかった場合、本プロジェクトは凍結し別事業へ」など (実行はしないとしても、コミットの重みを上げる)
5. 期日延長は **絶対にやらない** を `anti-goals` に明記
6. 逆算スケジュール (5/3 から日割り) を作る:
   - 4/28-29: P0 バグ修正
   - 4/30: 動画前処理 + 文面ドラフト
   - 5/1-2: 文面校正 + デプロイ確認 + 送信
   - 5/3: 全社送信完了 + 結果記録

#### シグナル

- 期日が「来月」「もうすぐ」「準備できたら」になっている
- カレンダーに期日のブロックが入っていない
- 期日条件が「launch する」のような **動詞 1 語** で終わっている (検証不可)
- 「もう少し時間があれば」を許容する空気

### 罠 P5: 既存資産 (流通チャネル / ドメイン知識) を見ていない

#### 発火パターン

「ターゲットユーザーをどこで見つけるか分からない」「営業先の連絡先がない」

#### 実体

builder は自分が **すでに保有している流通チャネル** をしばしば見落とす。本事例では:

- 創業者は別事業で **動画で職結び** (https://www.shoku-musubi.com/) を運営
- そこに **誌字脱字のある未編集動画を上げている企業が実在** = 解決したい問題が現実に存在することの 1 次情報
- 連絡先付きの企業リストが **既に手元にある**
- にもかかわらず、「ターゲットが分からない」と言いかけていた

つまり、launch の最大の制約だと思っていた **流通** が、実は **解決済み** だった。これに気付かないまま「DM を 3 件送って反応を見る」をしていた。

#### 構造的な原因

- **既存資産の見えなさ**: 自分が当然のように持っているものは「資産」として認識されない
- **新規プロダクトと既存事業の分離思考**: 別事業 = 別の話 と無意識に分離してしまう
- **第三者から見ると一目瞭然な結節点**: 自分では気付かない結節点が、他者の視点では即座に可視化される

#### 解毒手順

1. 新プロダクトを始める時、既存の **(a) 運営事業 / (b) ドメイン知識 / (c) 連絡先リスト / (d) 信頼資産** を 4 列で全列挙する
2. 各列について「新プロダクトのターゲットユーザーはここに居るか?」を Yes/No で答える
3. Yes が 1 つでもあれば、それが **第一の流通チャネル** (新規流通の探索より優先)
4. 自分の thinking 出力を **第三者視点でレビュー** してもらう (人間 / AI 問わず)。「あなたが既に持っているものは見えていない」前提で
5. 既存資産との **統合機能 (本事例: 動画で職結びとの自動連携)** は post-launch 課題に降ろす。launch 前は **手動で 5〜10 社選定** で十分

#### シグナル

- 「ユーザーをどこで見つけるか」が launch ブロッカーになっている
- 自分が運営する別事業 / コミュニティ / 知識領域を、新プロダクトと **無関係** だと脳内分類している
- 他者から「<既存資産> 使えばいいじゃん」と指摘されて初めて気付く
- 流通先探索に時間を使っているが、既存連絡先リストには手を付けていない

### 罠 P6: ペイン不在を打席数不足に誤帰因する (v1.1 で追加)

> **2026-05-04 B2B pivot 事案で発覚** (`knowledges/2026-05-04_b2b-pivot-ux-bugs-strategy-retrospective.md`). コールドメール 6 社送信→返信ゼロ。当初「6 社では打席不足 (罠 P3)」と再解釈しかけたが、根本原因は **ペイン validation 3 問が事前に立てられていなかった** こと (相手が払っているか / 困っていると言うか / 放置コストが数値化できるか)。

#### 発火パターン

- コールドメール / DM / outreach の返信率が 0
- 「もっと送れば反応あるはず」と打席数を増やそうとする
- 罠 P3 (「1 件で需要不在を結論するな」) を **逆方向に誤適用** して「需要不在の根拠が打席不足」と説明する

#### 実体

罠 P3 は **false negative on demand** (需要があるのに打席不足で見落とす) を防ぐためのもの。罠 P6 はその **逆** で、**false explanation by reach** (本当はペイン不在なのに打席不足のせいにする) という症状。両者は同じ「打席数」概念を扱うが、罠 P3 は「打席を増やせ」、罠 P6 は「**打席を増やす前に pain validation を再確認しろ**」と方向が逆。

#### 構造的な原因

- 罠 P3 を「打席増加」の正当化として記憶している → 返信ゼロで自動的に「打席を増やせばいい」と結論する
- ペイン validation を **outreach 開始前** に立てる習慣が無い (送ってから「需要あるかな」と考え始める)
- 「困っている人を探す」と「困っているか確認する」を混同している

#### 解毒手順

1. **コールドメール送信前にペイン validation 3 問を必須化**:
   - (1) 相手は **既に何らかの対価 (時間 / 金銭 / 注意)** を払っているか?
   - (2) 相手は「困っている」と **自発的に言葉にしている** か? (記事 / SNS / 公式発言で確認可)
   - (3) 放置した場合のコストを **数値化** できるか? (○○ 円損失 / ○○ 時間浪費 / ○○ 機会逸失)
2. 3 つ全て YES でないなら **送らない**。打席数を増やすのではなく **顧客プロファイルを変更** する
3. 返信ゼロを観測したら、まず罠 P6 (pain validation 不在) を疑い、**罠 P3 (打席不足) は二次仮説に降格**
4. Pain validation 3 問の答えを `contacts/<会社名>.md` に記録 (パーソナライズの証拠を観察→記述パイプラインで作る)

#### シグナル

- 「○○ 社に送ったが返信が無い。もっと送ってみよう」
- 送信前に「この相手は本当に困っているのか?」を確認していない
- 罠 P3 を引用して「6 社では足りない」と結論しようとしている
- ペイン定義が「自分が見たら困りそう」(推測) で、相手の発言/行動の証拠がない

#### 罠 P3 との違い (メタ整理)

| | 罠 P3 | 罠 P6 |
| -- | -- | -- |
| 防ぐ症状 | 1 件送って「需要なし」と結論 | 6 件送って「打席不足」と結論 |
| 解毒の方向 | 打席を **増やす** (5〜10 件) | 打席を **減らす** (顧客プロファイル変更) |
| 前提条件 | Pain validation 済み | Pain validation **未** |
| 適用順序 | Pain validation YES の **後** | Pain validation **の代わり** に打席で説明する誤用を防ぐ |

両罠を同じ場面で誤って混用しないよう、**「打席数を議論する前に Pain validation 3 問を通したか?」を必ず先に確認**。

## 🛡️ Launch 行動チェックリスト — 「launch まだ?」と感じた瞬間に全件回す

### A. 偽装ブロッカー検知 (罠 P1)

- [ ] 現在「launch ブロッカー」と認識している項目をリストアップした
- [ ] 各項目について「これは launch **後** に決められる判断か?」を Yes/No で書いた
- [ ] Yes だったものは `knowledges/open-questions.md` に降格して launch ブロッカーから外した

### B. もう一機能だけ防衛 (罠 P2)

- [ ] 残作業リストが期限から逆算して **3 つ以下** になっている
- [ ] 「これも入れたら」と思った機能を `anti-goals.md` に書いた
- [ ] MVP の定義が「感動機能完備」ではなく「信頼破壊バグなし」になっている

### C. 打席数 (罠 P3)

- [ ] 初回 launch で **5〜10 件以上** 同時送信する送り先リストを準備した
- [ ] 返信率の判定は **全件送信 + 1 週間後** までしないと決めた

### D. 期日コミット (罠 P4)

- [ ] 期日を **絶対日付 (年月日 + 曜日 + 時刻)** で書いた
- [ ] カレンダーアプリにブロックを入れた
- [ ] 期日条件を **複数の検証可能な完了項目** に分解した
- [ ] 期日延長を `anti-goals.md` に書いた

### E. 既存資産 (罠 P5)

- [ ] 既存の運営事業 / ドメイン知識 / 連絡先リスト / 信頼資産を 4 列で列挙した
- [ ] 各列で「ターゲットユーザーはここに居るか?」に答えた
- [ ] Yes だった列を **第一の流通チャネル** として明記した

### F. Pain validation (罠 P6 / v1.1 で追加)

- [ ] outreach 送信前に **ペイン validation 3 問** を `contacts/<相手>.md` に書いた:
  - [ ] (1) 相手は既に何らかの対価 (時間 / 金銭 / 注意) を払っているか?
  - [ ] (2) 相手は「困っている」と自発的に言葉にしているか? (記事 / SNS / 公式発言)
  - [ ] (3) 放置コストを数値化できるか? (○○ 円損失 / ○○ 時間浪費)
- [ ] 3 つ全て YES でないなら送信しない (打席を増やすより顧客プロファイル変更を優先)
- [ ] 返信ゼロを観測したら **罠 P3 (打席不足) ではなく罠 P6 (pain validation 不在) を最初に疑う**

## 🔍 既往事例: なぜ防げなかったのか / 既存原則との関係

### ケース 1: 本プロジェクト task_64〜71c (2026-04-22〜26)

**構造:** 12 タスク 3 日で UX 改善 / バグ修正を回したが、その間 **コールドメール送信は 0 件**。技術タスクは順調に進み、CLAUDE.md / souls / knowledges は厚く育ったが、**ユーザー検証の打席数は変わらず**。

**なぜ防げなかったか:**
- 既存 souls はすべて **「実装の質」** を扱う原則 (browser-runtime-asymmetry / requirement-translation-traps / spec-phase-hallucination / task-graph-execution-discipline)
- どれも「**実装が動くか**」を保証する原則であり、「**実装したものが触られているか**」は範囲外
- builder の「次のタスクを完遂する」サイクルが回り続け、その完遂自体が **launch 行動の代替** として機能してしまった (= 仕事した気持ちで一日が終わる)

**教訓:**
- 「実装の質」を保証する原則と、「launch 行動」を保証する原則は **直交軸**
- どちらか片方だけでは不十分。本書 (P1〜P5) は後者の最初の体系化
- セッション開始時の依存タスク確認 (`meta-task-graph-execution-discipline §ゲート 1`) と同じ強度で、**launch コミット日の確認** をルーチンに入れる必要がある

### ケース 2: /office-hours セッション自体 (2026-04-27)

**構造:** Whisper の精度設定が議論の中心になりかけた瞬間、`/office-hours` パートナーが「**それは launch 行動ではない**」と切り返したことで罠 P1 が顕在化。1 セッション内で罠 P1〜P5 すべてが浮上 → 期日コミット 5/3 で確定。

**なぜ自分一人で気付けなかったか:**
- 技術判断は builder の **得意な土俵** なので、無意識にそこに引き戻される
- 「精度設定の比較」は具体的・解析可能で気持ちが良い。「コールドメール送信」は不確実・拒絶可能性ありで気持ちが悪い
- 第三者 (パートナー / AI / 同僚) から「**それは launch ブロッカーではない**」と切り返されないと、自分だけでは罠 P1 から脱出できない

**教訓:**
- launch フェーズでは **第三者切り返し** を意図的に組み込む (本事例: `/office-hours` が機能した)
- 「自分の thinking には罠 P1〜P5 のいずれかが入っている」前提で、定期的に外部視点を入れる
- 1 人で考え込んでいる時間が長くなったら、それ自体が罠の発火サイン

### ケース 3: B2B コールドメール 6 社返信ゼロ → 罠 P6 発見 (2026-05-04 / v1.1 で追加)

**構造:** B2B pivot (動画で職結び 5〜10 社へコールドメール送信) で 6 社送信完了 → 返信ゼロ。当初「6 社では打席不足 (罠 P3)」と再解釈しかけたが、retrospective で **真因は pain validation の不在** だったと判明 — 送信前に「相手が払っているか / 困っていると言うか / 放置コスト数値化できるか」を検証していなかった。

**なぜ防げなかったか:**

1. **罠 P3 が「打席増加」の正当化として記憶されていた**: 「1 件で需要不在を結論するな (P3)」を学んだ結果、「返信ゼロ = 打席を増やせ」という安易な逆翻訳が脳内で発火
2. **罠 P3 自体は false negative on demand を防ぐが、その逆 (false explanation by reach) は未カバー** だった: 罠 P6 を新設するまで「pain validation 不在を打席不足で説明する」毒を防ぐ機構が無かった
3. **pain validation 3 問が outreach フェーズの強制機構に組み込まれていなかった**: 既存チェックリスト C (打席数) は「5〜10 件以上送る」しか問わず、「送る前に pain を検証したか」を問わなかった

**教訓 (v1.1 で固定化):**

- **罠を学んだら、その逆方向の誤適用 (逆罠) も同時に検討する** (P3 と P6 はペア。片方だけでは毒)
- **outreach フェーズの強制機構に「送信前 pain validation」を必須項目として組み込む** (チェックリスト F)
- **返信ゼロを観測したら、まず pain validation 不在 (P6) を疑い、打席不足 (P3) は二次仮説に降格する** (順序が逆だと永遠に的外れの追加打席を投入する)
- パーソナライズの証拠は文面ではなく **観察→記述パイプライン** (`contacts/<会社名>.md`) で作る (`knowledges/2026-05-04_b2b-pivot-ux-bugs-strategy-retrospective.md` 参照)
