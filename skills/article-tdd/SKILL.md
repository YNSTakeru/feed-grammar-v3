# article-tdd

求人メディアの記事 (`public/articles/*.json` または `src/app/article/**/*.{js,tsx}`) を、ソフトウェア TDD と同じ感覚で**先にテストを定義 → 実装 → 走らせて緑にする**まで回す。
記事は「書いて終わり」ではなく**変更されるたびに再実行**するのが前提（タイトル1文字変えただけでも整合性軸/SEO軸が割れる）。

知見の出典: `knowledges/2026-05-21_surfing-article-iteration.md` (CP001〜CP020 / 9 commits / grok・Gemini レビュー)。あの 1 記事で踏んだ 5 つの罠 (OpenWork規約違反・タイトル本文乖離・愚痴フレーム・上から目線・過度な断定) を**他記事でも踏まないため**の汎化。

---

## ハードゲート (起動前に必ず確認)

- [ ] 対象記事のファイルパスが特定できている (例: `public/articles/<slug>.json`)
- [ ] その記事の**想定検索流入クエリ**を 1 つ以上ユーザーに宣言させている (例: 「サーフィン 休暇 福利厚生」)
- [ ] その記事の**ペルソナ**を 1 行で言える (例: 「波乗りが好きで転職を検討中の20代後半〜30代エンジニア」)

上記が欠けたら STOP。AskUserQuestion で 1 つずつ埋める。ペルソナ宣言なしの記事チェックは「独りよがり軸」が定義不能になるので必ず先に確定する。

---

## 実行フロー (TDD ループ)

```
1. Red:   8軸 × 各テストケースを順に検証 → 失敗を一覧化
2. Green: 最も影響の大きい1ファイル/1セクションだけ最小修正
3. Refactor: 直した結果が他の軸を壊していないか再走
4. Repeat: 全テスト PASS まで。3周しても収束しないなら BLOCKED 報告
```

ルール:
- **1ループにつき修正は1軸まで**。一気に全部直すと、なぜ通ったか/壊れたかが混ざって学習不能になる。
- **修正前後で同じテストを必ず再実行**。grep で検証可能な形で書く (後述)。
- **取り込まなかった指摘は記録**。`knowledges/` の「取り込まなかった提案」セクションに追記する慣習を踏襲。

## 検証軸 (8 axis × 各テストケース)

各軸は「観点 / NG パターン / 検証コマンド or 質問 / 修正の方向性」の4点セット。
PASS 基準は**grep またはユーザー目視で True/False が確定する形**で書く。「丁寧か」のような抽象判定は禁止 (AGENTS.md §4.4 spec ハルシネーション回避)。

### Axis 1: SEO 軸

タイトルで止まってクリックされるかが全て。記事の方針に引っ張られて CTR を下げる長文タイトルは即 BLOCK。

| Test | NG パターン | 検証 |
|------|------------|-----|
| T1-1 タイトル長さ | 全角35文字超 (スマホ検索結果で末尾省略) | `node -e "console.log([...タイトル].length)"` で確認、≤32 推奨 |
| T1-2 検索クエリ含有 | 想定流入ワードがタイトル/description に未出現 | `rg "<想定クエリ語1> .* <想定クエリ語2>" <file>` |
| T1-3 description クリック誘発 | 「〜です」だけの説明文・決めつけ・煽り | grok ではなくユーザー判断: 「自分が検索してこのスニペットを見たらクリックするか?」 |
| T1-4 構造化データ | 求人/企業比較記事に `JobPosting` or `Article` schema 欠如 | `rg "application/ld\+json" <page-component>` |

修正方針: タイトルは**短く・問い形・決めつけない**。「〜できない会社が多い」のような断定は外す (この罠は CP019 で踏んだ)。

### Axis 2: コンプライアンス / 法令軸

OpenWork・Glassdoor・転職会議など**口コミサイトの数値や口コミ文の引用は商業利用規約違反リスク**。Perplexity 等の調査 AI が出してきた数値もそのまま転載しない。**Openwork は調査用、本文の数値は企業公式 1 次情報で裏取り**が鉄則。

| Test | NG パターン | 検証 |
|------|------------|-----|
| T2-1 口コミサイト引用なし | "OpenWork" "Glassdoor" "転職会議" "ライトハウス" 等の語が本文に出現 | `rg -i "openwork\|glassdoor\|転職会議\|ライトハウス\|キャリコネ" <file>` で 0 件 |
| T2-2 数値の出典明記 | 「有給消化率79.4%」のような具体数値に出典 (公式IR/人的資本開示/採用ページ) が無い | 数値を grep して直後に出典 URL or 公式名があるか目視 |
| T2-3 1 次情報裏取り | Perplexity / ChatGPT 出力をそのまま記事化 | 各事実につき「企業公式ページで自分の目で確認したか?」をチェックリスト化 |
| T2-4 過度な企業評価 | 「青信号」「ブラック」「実態は〜」など断定的色分けがクレームリスク | `rg "ブラック\|実態は\|の真実" <file>` 0 件、評価語は留保付きに変換 |
| T2-5 アフィリ属性 | 送客リンクが `<AffiliateLink />` 経由でない or `rel="sponsored noopener"` 欠落 | `rg "AffiliateLink" <component>` でヒット、生 `<a>` タグでの送客は BLOCK |

修正方針: 口コミサイト経由の情報は**全削除**。グレーゾーン回避を最優先 (CP003 で踏んだ罠)。

### Axis 3: 整合性軸 (タイトル ⇔ リード ⇔ 本文 ⇔ 結論)

一番大きなリスクは**タイトルで約束したことを本文で体現できていない**こと。grok が「タイトルが強すぎる」と毎回指摘していた問題は、実は**リード文の矛盾**だった (CP005)。タイトル先行ではなく**本文で何を体現できるか確定してからタイトル**を書く。

| Test | NG パターン | 検証 |
|------|------------|-----|
| T3-1 タイトル ⇔ リード矛盾 | タイトル「Aの有無より大切なこと」、リード1文目「A はごくわずかです」 | リード冒頭3文を読み返して矛盾語 (「しかし」「ガッカリ」)が出ていないか目視 |
| T3-2 タイトル約束 ⇔ 本文構成 | タイトルで「特徴」と謳いながら本文が事例集だけ | タイトル名詞 (特徴/比較/見分け方/ステップ) ごとに対応セクションがあるか |
| T3-3 件数の整合 | タイトル「6選」、本文5社 | `rg "(\d+)選\|(\d+)社\|(\d+)つの" <title>` の数 = 本文の項目数 |
| T3-4 結論がタイトルの問いに答える | タイトルが問いなのに最終セクションで答えてない | 最終セクション末尾を読み、タイトルへの回答になっているか |

修正方針: タイトル変更時は**リード3文 + 結論を必ずセットで再走**。

### Axis 4: 誠実さ軸 (ネガティブ感情 → 知的好奇心 変換)

不安・怒り・嫉妬を煽る情報は**Perplexity での情報収集時は有効**だが、**記事化するときは知的好奇心フレームに変換**する。愚痴フレームは共感を生むが「どうせ無理」が連鎖して CVR を下げる (CP011 で実証)。

| Test | NG パターン | 検証 |
|------|------------|-----|
| T4-1 諦め語の禁止 | 「どうせ」「ムリ」「絶望」「ガッカリ」「期待するだけ無駄」 | `rg "どうせ\|ガッカリ\|期待するだけ\|絶望\|無駄" <file>` 0 件 |
| T4-2 怒り煽動の禁止 | 「許せない」「酷い」「最悪」など他者批判形 | `rg "許せ\|酷い\|最悪\|ひどい" <file>` 0 件 |
| T4-3 観察・問い形変換 | ネガティブ事実を断定 (「申請しても上司に白い目で見られる」) | 「〜が実際に申請できたサーファーは何人いるのか」のような**問い形**に書き換える |
| T4-4 比較対象の対称性 | 競合企業を不当に貶める比較 | 比較は「A は X / B は Y」の事実併記、勝敗判定は読者に委ねる |

修正方針: ネガティブ事実は消さず、**観察フレーム or 構造的問い**に変換する。「上司ガチャ」→「評価設計が成果ベースか出席ベースか」のように人 → 仕組みへ視点を移す (CP018)。

### Axis 5: 信頼性軸 (検証できないことは断定で書かない)

検証不能な主張を断定すると、1 件でも反例が出た瞬間に**メディア全体の信頼が崩れる**。「決めつけてないか」「反例 1 件で崩れる主張になってないか」を毎回確認。

| Test | NG パターン | 検証 |
|------|------------|-----|
| T5-1 全称量化の濫用 | 「全社が」「必ず」「絶対」「100%」 | `rg "全社\|必ず\|絶対に\|100%\|誰でも" <file>` ヒット箇所をレビュー、留保語 (多くの/概ね/傾向として) に置換 |
| T5-2 出典なし数値 | 数値が本文にあるが出典 URL/公式名なし | 数値を全 grep し、出典が直後 or 脚注にあるか確認 |
| T5-3 推測と事実の区別 | 推測を断定で書く (「だから〜だ」) | 推測には「と推測される」「公式情報なし」「2026年5月時点」を付与 |
| T5-4 ガチャ概念の排除 | 「上司ガチャ」「会社ガチャ」など運任せフレーム | Gemini 穴① 指摘 (CP015) と同じ。仕組み・評価設計の話に置換 |

### Axis 6: 可読性軸 (ユーザー主体)

上から目線・先生口調・専門家マウントは**読者を確実に離脱させる**。命令形 (「確認してください」) より参加形 (「紐解いてみましょう」) が有効。

| Test | NG パターン | 検証 |
|------|------------|-----|
| T6-1 命令形の最小化 | 「〜してください」「〜が重要です」「必ず〜しましょう」連発 | `rg "してください\|が重要です\|必ず.*しましょう" <file>` カウント、本文1セクションに2件以上は要修正 |
| T6-2 専門用語の言い換え | 「コアタイム」「人的資本開示」を初出時に注釈なし | 初出語に括弧で簡易説明があるか目視 |
| T6-3 一文の長さ | 一文が 80 文字超で読点だけで繋がる | 視認、80 文字超は分割 |
| T6-4 ユーザー主体の主語 | 主語が「私たち」「筆者」「我々」中心で「あなた」「読者」が出てこない | `rg "あなた\|自分\|ご自身" <file>` のヒット数が「私たち\|筆者」より多いか |

### Axis 7: ペルソナ軸 (独りよがりチェック)

書き手の「言いたいこと」と読者の「知りたいこと」のギャップは**毎稿生まれる**。事前にペルソナを 1 行宣言したら、本文を読みながら**そのペルソナがどこで離脱するか**を逐一マークする。

| Test | NG パターン | 検証 |
|------|------------|-----|
| T7-1 ペルソナ 1 行宣言 | 記事冒頭または design doc にペルソナ未記載 | ハードゲートで確定、未確定なら STOP |
| T7-2 ペルソナの前提知識 | ペルソナが知らない用語を説明なしで使用 | 例: エンジニア向け記事に「リファラル採用」 → 注釈or言い換え |
| T7-3 ペルソナの次アクション | 読み終わった読者が次に何をすればいいか不明 | CTA + closing_text に具体行動 (「比較リスト作成」「公式採用ページ確認」) があるか |
| T7-4 独りよがり語の検出 | 書き手の業界内ジャーゴン (「グロース」「PMF」「リファラル」) が無注釈 | カスタム辞書で grep |
| T7-5 決めつけ排除 | 「サーファーは皆〜」「エンジニアなら〜」のステレオタイプ | `rg "は皆\|たちは全員\|なら絶対" <file>` 0 件 |

### Axis 8: マネタイズ整合軸 (AGENTS.md §2 ハードルール)

AGENTS.md §2 と重複するが、本スキル単独で記事を緑にできるように再掲。

| Test | NG パターン | 検証 |
|------|------------|-----|
| T8-1 CTA 同一 viewport | 動画埋め込み or 主要事例の直後に CTA がない | 該当コンポーネント目視、CTA を viewport 内に配置 |
| T8-2 AffiliateLink 経由 | 送客リンクが生 `<a>` で `rel="sponsored"` 直書き | RULE M-1 違反 → BLOCK |
| T8-3 CTA 文言の心理ハードル | 「求人を見る」のような直接表現 | 「自分に合うかチェックする」「現在の採用状況を見る」等に置換 |
| T8-4 計測タグ | クリックが GA4 `affiliate_link_click` で記録される | `rg "affiliate_link_click" src/components/AffiliateLink.js` でヒット必須 |

### Axis 9: ペルソナ憑依最終チェック (サブエージェント / TDDループ完了後の最終ゲート)

8軸 grep がすべて PASS しても、**ペルソナが実際に最後まで読んで CTA を踏むか**は別問題。Axis 7 の T7-1〜T7-5 は「ペルソナが理解できるか」までしか測れず、**離脱予測・温度測定**が抜けている。

`knowledges/2026-05-25_article-tdd-meta-learnings.md` 知見5: 外部AI (grok 等) に「ペルソナに刺さるか」を聞くと永久共感ループに陥るが、**サブエージェントを内部閉ループで起動する**と評価関数を制御できる。

#### 起動条件
- Axis 1〜8 すべて PASS した直後 (TDDループの最後)
- **1 タスクにつき 1 回限り**。永久ループ防止のため再走しない
- 修正が必要なら Axis 9 の指摘を 1 つだけ取り込んで Axis 3/4/6 を再走 → 再 Axis 9 は行わない

#### 起動方法

```
task agent_type=general-purpose model=Codex-sonnet-4.6 mode=sync
  name: persona-readthrough
  prompt:
    あなたは以下のペルソナを完全に内面化してください:
    <ペルソナ 1 行宣言を貼り付け>

    そのペルソナとして、以下の記事を頭から最後まで通読してください:
    <記事ファイルパス or 全文>

    報告フォーマット (この形式厳守、印象論禁止):
    1. 段落単位で「離脱したいと感じた箇所」を行番号付きで列挙 (なければ「なし」)
    2. 温度が変わった箇所 (好転/悪化) を行番号付きで列挙
    3. 次アクションを起こしたくなった箇所 (CTA 直前等) を行番号付きで列挙
    4. 最後に「自分なら CTA を踏むか」を YES/NO で回答 + 理由 (3行以内)
    5. もし NO なら、最低限どの1段落を変えれば YES になるかを 1 箇所だけ提案

    禁止事項:
    - 「もっと共感を」「もっと温度を」のような無限延長指摘
    - 「先生口調」「硬い」のような grep 不能な印象論
    - 指摘は必ず行番号付きで具体提案を伴うこと
```

#### 採否判断
- **YES 回答** → DONE 確定、knowledges に「Axis 9 PASS」を記録
- **NO 回答** → 提案された 1 箇所だけ修正、関連軸 (Axis 3/4/6) を再走、Axis 9 は再走しない
- **行番号なし指摘 / 印象論指摘** → 無視 (フォーマット違反として却下)
- **永久ループ警報**: サブエージェントが「もっと共感」型を返したら、プロンプトのペルソナ内面化が失敗している → ペルソナ 1 行宣言の見直し、または NO 判定を採用しないで DONE 確定

#### なぜ外部AI (grok) ではなくサブエージェントか
- **内部閉ループ**: プロンプトでペルソナを完全に固定できる (grok は都度ペルソナを忘れる)
- **行番号付き報告必須**: 印象論を排除できる (プロンプトで強制)
- **YES/NO 判定**: 「もっと共感」型の無限延長を構造的に出させない
- **1 回限り**: TDDループの最後に 1 回。永久共感ループ (知見1) に陥らない
- **AGENTS.md §4.5 と整合**: 外部AIの仮説は参考、ドメイン側 (本スキル) が最終決定権を保持

## 実行 (どう走らせるか)

### 初回 (新規記事)

1. AskUserQuestion で**ペルソナ・想定流入クエリ・タイトル候補**を確定 (ハードゲート)
2. **本文ドラフト → Axis 1〜8 を Test 順に走らせる** (この順番が重要: SEO で外したらタイトルから直し、コンプラで外したら全削除、整合で外したら本文書き直し、と上流ほど影響大)
3. Red のテストを 1 つずつ最小修正 → 再走 → Green
4. **Axis 1〜8 全 Green になったら Axis 9 (ペルソナ憑依サブエージェント) を 1 回だけ起動**
5. Axis 9 YES → DONE / Axis 9 NO → 提案 1 箇所だけ修正 → Axis 3/4/6 再走 → DONE (Axis 9 再走禁止)
6. 出力末尾に**残課題一覧** (今回取り込まなかった指摘 + 理由) を `knowledges/<date>_<slug>-iteration.md` に記録

### 再実行 (既存記事を編集したとき)

タイトル変更 → Axis 1, 3 必須再走
本文編集 → Axis 3, 4, 5, 6 必須再走
新企業/事例追加 → Axis 2, 5, 7 必須再走
CTA 変更 → Axis 8 必須再走

「全軸常時再走」ではなく**変更箇所と関連する軸だけ走らせる**。CI に乗せる場合は記事ファイルの diff から影響軸を判定する。

### クロスモデル使用時 (grok / Gemini / Codex / Perplexity)

- **問題発見ツールとしては有効**。「全部直せ」と言われても採否判断はドメイン側
- **採用基準**: 「なぜそうすべきか」の根拠が SEO/CVR/ペルソナと整合するか (AGENTS.md §4.5 と CP020 の教訓)
- 取り込まなかった指摘は必ず**理由付きで記録**。後で同じ提案が来たときに即判断できる

#### 永久共感ループ警告 (CP022 / `knowledges/2026-05-25_article-tdd-meta-learnings.md` 知見1)

外部AIは**評価関数が「共感の濃さ」に固定**されていて、3 ラウンド以上回すと「もっと共感 / もっと温度 / もっと膨らませろ」が無限に返ってくる。字義実装すると共感セクションが本文 30% を超え、解決パートに到達する前に読者離脱 → CVR ゼロ (CP011 そのもの)。

検出ルール:
- 同じ部分への再膨らませ指摘が来た = **永久ループ警報**
- N ラウンド目の指摘が「ここをもっと厚く」型で、N-1 ラウンドで既に厚くしている
- ペルソナの「次アクション温度」(Axis 7 T7-3) が一度も話題に上がらない

対処:
- **3 ラウンド目以降の「もっと共感」型指摘は却下デフォルト**
- ただし**橋渡し文の書き換え** (共感→構造への接続改善) は採用可
- 共感セクションが本文 30% を超えたら、それ以降の共感拡張指摘は全却下

#### 外部AI指摘の事実確認手順 (知見2-3)

外部AI (特に grok) は**「タイトル=本文要約」モデル**で読むため、補完関係タイトルや長文記事を構造的に誤読する。指摘を受けたら以下を必ず通す:

1. **行番号特定**: 「冒頭で〜」「すぐに〜」型指摘は、実際の該当箇所を `grep -n` で行番号確認
2. **構造再描画**: H1 → リード → H2-1 → … と構造を行番号付きで書き出す
3. **事実誤認の弾き**: 「実はそこは既に書いてある / 60行下 / H2を1つ挟む」が判明したら**却下、行番号付きで knowledges に記録**
4. **補完関係宣言**: タイトル=入口 / 本文=独自構造 の場合、その関係を knowledges 冒頭に書いて反論材料を予約しておく

#### grep 不能な抽象指摘の扱い (知見4)

「先生口調」「分析的すぎる」「硬い」のような印象論は **AGENTS.md §4.4 spec ハルシネーション回避**に抵触し、永久に「まだ硬い」と言われ続けるリスク。

対処:
- 印象論指摘は**関連する具体軸 (Axis 6 T6-1 など) に翻訳**して grep で True/False 確定
- 具体軸 grep で 0 件 PASS なら**確定却下**
- 翻訳不能な印象論は**却下デフォルト**
